# FileSync v3.0：低内存存储与扫描架构

> 状态：实现规范（Normative）
> 产品约束：Windows x64、.NET 8、无 SQLite、低内存优先。

## 1. 设计目标

FileSync 的低内存设计不是“尽量少分配”，而是对所有随文件数量增长的内存结构设定明确上限，并将完整状态放在磁盘上。文件数量可以影响扫描时间和磁盘索引大小，但不应导致进程把所有路径、差异或事件常驻内存。

禁止：
- 一次性递归枚举整棵目录树并构造全量 List/Dictionary；
- 将整个文件内容读入内存；
- 无界 Channel、队列、Task、重试集合；
- 将所有待执行计划保留为内存对象；
- 使用大对象缓存掩盖存储设计问题。

## 2. 无 SQLite 状态存储

当前产品决定使用纯托管 Journal + Snapshot，不引入 SQLite。该方案意味着 FileSync 必须承担轻量数据库的正确性责任，不能把它描述成“无数据库复杂度”。

### 2.1 建议磁盘布局

~~~text
%LocalAppData%/FileSync/
  manifest.json
  journal/
    segment-000001.log
    segment-000002.log
  snapshots/
    baseline-000001.idx
  operations/
    inflight.log
  conflicts/
  trash/
  logs/
~~~

实际 data 根目录必须可配置，且必须位于所有同步 root 之外；启动时进行规范化路径和重叠检查。

### 2.2 Journal 记录格式

记录至少包含：
- Magic、FormatVersion、RecordType；
- Sequence、PayloadLength、TaskId；
- Payload；
- CRC32C 或等效校验。

要求：
- 单条记录有最大长度上限；
- 追加式写入，禁止原地改写历史记录；
- 启动重放验证序号、长度、校验和；
- 尾部部分写入可截断到最后一条完整记录；
- 中间损坏不能简单跳过继续写，应进入只读诊断/恢复模式；
- 记录版本向前兼容策略明确，未知字段可忽略，未知关键版本拒绝写入。

### 2.3 Snapshot 与索引

- Snapshot 是某个 Journal Sequence 的完整基线快照。
- 先写临时 Snapshot，Flush、校验、重新读取验证后，再原子更新 manifest。
- 只有 manifest 指向的新 Snapshot 可用后，才允许清理被覆盖的旧段。
- 索引采用磁盘有序段或 B+Tree/Sorted Segment 等可分页结构；第一版优先实现简单可验证的有序段，不要过早引入复杂自研索引。
- 内存只保留固定容量的页缓存和热点路径缓存；缓存逐出不影响正确性。
- 任何索引缓存都必须可由 Snapshot + Journal 重建。

### 2.4 状态提交者

- 每个 Task 一个逻辑状态提交者，串行追加记录。
- 扫描器、哈希器、传输 Worker 不得直接写 Base。
- 状态提交者使用单一有界输入队列；队列满时施加背压，不能丢状态事件。
- 日志、统计等低优先级信息可分批写入，但 Operation 与 Base 记录必须有明确持久化等级。

## 3. 流式扫描

- 枚举器按目录逐层推进，不构造全局树。
- 同级 A/B 项目使用 merge-walk；目录项排序只保留当前目录所需的有界缓冲。
- 若端点枚举不保证排序，则使用有界内存排序或磁盘外部排序；不能假定所有 SMB 服务端天然有序。
- 单目录项目数超过内存阈值时，写入临时排序段并归并。
- 扫描进度写入磁盘 ScanCheckpoint；中断后可以重扫未完成目录，但未完成扫描不能证明删除。
- 扫描结果以小批次写入磁盘临时索引，最终完成且校验后再作为该 ScanEpoch 的有效观察结果。

## 4. 计划与任务队列

- SyncPlan 持久化到磁盘计划段；引擎只加载当前执行窗口。
- 计划分批生成、分批执行；执行结果及时写入 journal 并释放对象。
- Worker 数量固定上限；默认传输并发 1，经过真实 NAS 与内存基准后可调到 2。
- Dirty 事件队列、重试队列、路径锁表和冲突缓存均有容量上限。
- 队列溢出必须设置 NeedReconcile 标记；不能静默丢弃并继续宣称同步完成。
- 重试任务按磁盘队列调度，避免长时间失败项目占满内存。

## 5. 内存预算

初始预算是设计目标，必须在真实 .NET 8 发布构建上测量。不得将以下数值误写为已经实现的性能承诺。

| 子系统 | 设计预算 | 上限策略 |
|---|---:|---|
| Core/调度基础对象 | 4 MB | 避免全局缓存 |
| 热点索引页缓存 | 8 MB | 固定页数，LRU 淘汰 |
| Dirty/重试/路径锁 | 4 MB | 有界；溢出触发补偿 |
| 传输缓冲 | 1–2 MB | 128/256 KB × 1–2 worker |
| 哈希/扫描临时对象 | 4 MB | 分批、及时释放 |
| 运行时与其他托管对象 | 实测 | 不能用托管堆预算代替进程预算 |

测量必须分开报告：
- Managed Heap / GC Heap；
- Working Set；
- Private Bytes；
- Native Heap；
- 线程栈与句柄；
- FSW/系统内核 Nonpaged Pool（通过系统工具单独测量，不计入进程 Working Set）。

GC HeapHardLimit 只限制托管堆，不能作为整个进程内存上限证明。FSW 缓冲区、线程栈、原生库、映射文件和内核缓冲都要纳入整体观察。

## 6. 性能与内存验收

固定基准环境并记录 Windows 版本、CPU、RAM、磁盘、.NET 补丁版本、NAS 型号/协议、文件数量和目录分布。

建议测试集：
- 1 万、10 万、100 万文件；
- 宽目录与深层目录；
- 大量 4KB 小文件与若干 1GB 大文件；
- NAS 低延迟/高延迟/断线；
- 冷启动与热缓存；
- 首次全量扫描、单文件变化、全量审计。

验收重点：
1. 文件数增长时 Working Set 不按文件数线性增长；
2. 峰值内存与配置的缓存、队列、并发上限一致；
3. 队列溢出后能通过补偿扫描恢复；
4. 大文件复制不发生整文件缓冲；
5. 长时间运行没有持续内存爬升；
6. 扫描中断不推进不完整 Base。

产品当前目标（引擎稳态 <40 MB、普通同步峰值 <50 MB、UI 4–7 MB）保留为目标值，但须先形成真实基线报告；报告不达标时优化或向用户明确差距，不得通过隐藏 Native/Kernel 内存或改变测量口径宣称达标。

## 7. .NET 8 约束与生命周期风险

项目按用户已确认的要求使用 .NET 8，不在本次架构文档中擅自升级目标框架。需要明确记录：截至 2026-11-23，Microsoft 已于 2026-11-10 结束 .NET 8 支持，后续不再提供该版本安全修复和技术支持。发布前必须由产品负责人确认接受此风险，并建立未来升级评估门槛。

Native AOT 不是默认方案。只有在相同功能、相同测试数据下，对比普通自包含发布与 Native AOT 的启动时间、Working Set、Private Bytes、包体积、兼容性和诊断能力后，才决定是否采用。
