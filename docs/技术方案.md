## 1. GitHub 现有方案调研

### 1.1 结论先行

| 类别 | 代表项目 | 可借鉴 | 能否直接用 |
|---|---|---|---|
| 成熟独立同步引擎 | **syncthing/syncthing**（90,725★，Go） | 增量扫描、忽略规则、冲突副本命名、版本目录、断点/断电恢复 | 不能直接嵌 .NET；可作为行为参照与“兜底方案” |
| 双向脚本方案 | **deajan/osync**（998★，Shell） | 两遍收敛式同步（先扫描计划再执行）、删除保护、故障容错 | 参考算法，不嵌 |
| C# 同步应用 | **POW-Software/ByteSync**（177★，MIT，C#） | 分层架构（Client/Common/ServerCommon）、校验清单(Inventory)模型、块级指纹、临时文件落盘策略 | 代码可读，适合抄结构；协议层过重，不适合“本地↔SMB 同机”场景 |
| 轻量 C# 同步库 | **dvoituron/BlinkSyncLib**（27★，2015 停更） | 最小实现：扫描→比较→复制 | 太旧，仅作入门参考 |
| 现代 .NET 同步库 | **Oire/sharp-sync**（7★，Apache-2.0）、**sunsided/crossbow**（SQLite 目录 + 哈希） | 存储后端抽象、哈希比较 + SQLite 编目 | 可读其目录库设计；成熟度低，不建议依赖 |
| 实时文件同步 | **no-src/gofs**（526★，Go，fsnotify） | 事件驱动 + 防抖 + 定时全量兜底扫描 | 参考事件模型 |
| 状态库设计 | **LINBIT/csync2**（163★，C，librsync + 状态数据库） | “每文件一条 last-sync 状态”的两库比较模型（本方案核心） | 参考数据模型 |
| 云盘/网盘同步客户端 | **trueai-org/mdrive**（238★，C#）、**SparkleShare**（5,006★，C#） | 托盘/服务形态、日志与通知、状态可视化 | 参考外壳结构 |

**为什么不直接用现成项目：**

1. Syncthing 需要两端都装 agent（NAS 需能装 Docker/二进制），且它是“自有协议传输”，不走你已映射的 SMB 盘；你的诉求是“利用现有映射盘，不改造 NAS”。
2. FreeFileSync/RealTimeSync、robocopy /MIR 只能做单向镜像或“无状态覆盖”，**没有 last-sync 状态库就无法判断“谁改的、谁该覆盖谁”**，两端都改会静默丢数据。
3. 因此自研的合理价值点只有三个：**三方状态比较（base/local/remote）、SMB 编辑中文件的完成判定、可审计日志**。其余全部复用既有实现思路，不重复造轮子。

### 1.2 从调研中固化下来的设计原则

1. **状态化同步（三方比较）**：库中为每条相对路径保存 `base 快照`（上次同步完成时的哈希与时间戳），比较 `local` 与 `remote` 各自相对 `base` 的变化，得出动作。csync2 / Syncthing / osync 全部是这个模型。
2. **计划-执行分离**：先产出完整 `SyncPlan`（含 dry-run 输出），再执行，便于审计、限速、断点续传、用户预演（osync 两遍收敛、ByteSync Inventory 思想）。
3. **事件驱动 + 周期兜底**：事件不可靠（SMB 掉线、缓冲溢出），必须配合定时全量/增量校验扫描（gofs、Syncthing 的 rescan 间隔）。
4. **冲突不覆盖，产生副本**：`name.conflict-YYYYMMDD-HHmmss-<side>.ext`（Syncthing 命名习惯），可配置策略。
5. **删除进回收区**：本地 `.filesync-trash/<timestamp>/` 保留 N 天，而不是直接删。
6. **全程流式**：任何“读文件进 byte[]”的地方都是设计错误（ByteSync/sharp-sync 都是流式 + 增量哈希）。

## 2. 需求拆解与关键难点

| 需求 | 难点 | 方案落点 |
|---|---|---|
| 本地文件夹 ⇄ NAS 文件夹双向同步 | 双向必须知道“上次同步状态”，否则无法区分修改方 | SQLite 状态库 + 三方比较（§6） |
| 记录同步日志 | 既要人读又要可查询、可审计、可控体积 | SQLite 日志表 + Serilog 滚动文件（§8） |
| 网盘中文件“正在编辑”时不打断、编辑完成后自动同步 | Office/WPS 会先建 `~$` 锁文件、持续写盘、最终 rename，事件洪泛且文件常被独占 | 事件防抖 + 独占锁探测 + `~$` 锁文件感知 + 稳定窗口（§7.3） |
| 内存占用小、不 OOM | 大文件、海量小文件、事件洪泛、并发复制 | 流式缓冲 + ArrayPool + 有界队列 + 有界并发 + GC 配置（§9） |
| .NET 开发、用本机 SDK | SDK 仅 8.0.406 | `net8.0` + `PublishSingleFile`/`self-contained`（§10） |

**必须提前承认的物理限制**

- SMB 上 `FileSystemWatcher`（由 `ReadDirectoryChangesW` 实现）**事件会丢**：服务端缓冲溢出（`InternalBufferSize` 默认 8KB，最大 64KB）、网络抖动、NAS 端 SMB 实现差异。→ 必须有兜底扫描。
- 跨 SMB 的 `LastWriteTime` 精度可能被服务端取整到 1–2 秒（部分 NAS/Samba 配置）。→ 时间比较留容差，最终以哈希为准。
- NAS 侧若同时有人手工改文件，同步器无法“先锁后改”。→ 冲突策略 + 副本，而不是假装能保证强一致。

## 6. 核心算法：三方比较（本方案的心脏）

### 6.1 状态库表结构

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;

-- 每个相对路径一行：上次成功同步后的“共同基线”
CREATE TABLE sync_record (
    rel_path        TEXT PRIMARY KEY,          -- 统一为正斜杠、大小写不敏感（NAS 多为 Linux/Samba）
    kind            INTEGER NOT NULL,          -- 1=File 2=Dir
    size            INTEGER NOT NULL,
    local_mtime     INTEGER NOT NULL,          -- UTC ticks
    remote_mtime    INTEGER NOT NULL,
    content_hash    TEXT,                      -- 基线内容哈希（空=仅元数据一致）
    local_file_id   TEXT,                      -- 本地 NTFS FileId（改名检测用，可空）
    remote_file_id  TEXT,
    last_sync_at    INTEGER NOT NULL,
    last_op         INTEGER NOT NULL,          -- 1=Push 2=Pull 3=Both-Equal
    deleted         INTEGER NOT NULL DEFAULT 0 -- 墓碑：等待对端确认删除
);

CREATE TABLE sync_log (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    ts           INTEGER NOT NULL,
    level        TEXT NOT NULL,                -- Info/Warn/Error
    rel_path     TEXT,
    op           TEXT NOT NULL,                -- Scan/Push/Pull/Delete/Conflict/Skip/Error
    direction    TEXT,                         -- LocalToNas / NasToLocal
    bytes        INTEGER,
    duration_ms  INTEGER,
    hash         TEXT,
    message      TEXT,
    run_id       TEXT                          -- 一次同步会话聚合
);
CREATE INDEX ix_log_ts ON sync_log(ts);
CREATE INDEX ix_log_path ON sync_log(rel_path, ts);

-- 未完成的复制，用于断电/断网恢复
CREATE TABLE inflight (
    rel_path TEXT PRIMARY KEY, direction INTEGER, temp_path TEXT,
    started_at INTEGER, bytes_done INTEGER
);
```

> 只存元数据：1 万条记录约 1–2 MB，10 万条约 10–20 MB，与文件内容大小无关。

### 6.2 动作决策矩阵

令 `L`=本地当前指纹，`R`=远端当前指纹，`B`=基线（`sync_record`）。

| B 存在 | L==B | R==B | 语义 | 动作 |
|---|---|---|---|---|
| 否 | – | – | 新文件只在本地 | `Push`（远端无同名） |
| 否 | – | – | 新文件只在远端 | `Pull` |
| 否 | – | – | 两端都有但不同 | `Conflict`（默认保留双方） |
| 是 | 是 | 是 | 未变 | `None` |
| 是 | 否 | 是 | 本地改 | `Push` |
| 是 | 是 | 否 | 远端改 | `Pull` |
| 是 | 否 | 否 | L==R（两端改成了同样内容） | `UpdateBase`（不传输） |
| 是 | 否 | 否 | 都改且不同 | `Conflict` |
| 是 | 是 | 消失 | 远端删 | `DeleteLocal`（进回收区） |
| 是 | 消失 | 是 | 本地删 | `DeleteRemote`（远端进回收区/或直接删，可配） |
| 是 | 消失 | 消失 | 都删 | `RemoveRecord` |
| 是 | 消失 | 否 | 本地删 + 远端改 | `Conflict`（保守：改内容拉回本地） |

**删除必须走“墓碑确认”**，否则 NAS 断连时扫描到“远端全空”会清空本地：扫描前校验挂载点可用性（§7.2 探针），且当**一次扫描中远端删除比例 > 阈值（默认 25% 或 100 个文件）时，暂停并告警**，需要 `--force` 才执行。

### 6.3 指纹与比较成本（三级漏斗，决定性能）

```
Level 0：size 不同 → 一定不同（O(1)）
Level 1：size 相同 && |mtime_local - mtime_remote| <= 2s && mtime 与基线一致 → 视为未变（O(1)）
Level 2：size 相同但 mtime 变了 → 计算 “快指纹”：size + 前 64KB + 后 64KB 的 XxHash64（O(128KB)）
Level 3：快指纹不同/缺失基线 → 全文件 SHA-256（流式，仅对真正要变动的文件做）
```

- 大文件（视频/镜像）几乎都能在 Level 1/2 收敛，避免每次扫描重读几百 GB。
- 全量哈希只在**首次建库**（一次性）与**冲突判定**时发生。
- 首次建库支持 `--hash-mode metadata|quick|full`；默认 `quick` 并后台补齐 `full`（补齐时按 4 路并发限速）。

### 6.4 改名/移动检测（省流量关键）

同一扫描批次内，若出现 `1 个删除 + 1 个新增` 且 `size` 相同、`quick/hash` 相同 → 视为 `Move`：

- 本地改名 → 远端 `File.Move`（SMB 同卷 rename 为元数据操作，几乎零流量）。
- 远端改名 → 本地 `File.Move`。
- 本地 NTFS 可用 `FileId` 直接识别移动（成本 O(1)）；SMB 侧 `FileId` 不稳定就退化到哈希匹配。

### 6.5 计划与执行

```csharp
public sealed record SyncPlan(IReadOnlyList<SyncAction> Actions, PlanStats Stats);
public enum ActionKind { Push, Pull, DeleteLocal, DeleteRemote, MoveLocal, MoveRemote,
                         UpdateBase, Conflict, Skip, CreateDir, DeleteDir }

// 执行顺序（重要）：
// 1. CreateDir（按深度升序） 2. Move 3. Push/Pull（大文件先/后按配置） 4. Delete（按深度降序） 5. UpdateBase
```

- 执行前写 `inflight`，执行后同事务更新 `sync_record` + 写 `sync_log`；崩溃后启动时按 `inflight` 清理 `.filesync-tmp` 残留。
- 单个文件失败**不中断整轮**，记 `Error` 并进入“失败重试队列”（指数退避 5s/30s/2min，最多 N 次）。

## 7. 实时性设计与“编辑完成后再同步”

### 7.1 监听器

- 每侧一个 `FileSystemWatcher`：`IncludeSubdirectories=true`，`NotifyFilter = FileName | DirectoryName | LastWrite | Size`。
- `InternalBufferSize = 64KB`（最大值，降低溢出概率），并订阅 `Error`（缓冲溢出）→ 立即触发一次增量兜底扫描 + 记录 `Warn`。
- 远端监听路径**优先用 UNC**（`\\NAS\share\folder`），盘符路径在启动时用 `WNetGetConnection` 解析为 UNC；解析失败（如未映射）则按配置直接报错退出，绝不“静默不同步”。

### 7.2 挂载点健康探针（防误删的前提）

每轮扫描前：

1. `Directory.Exists(remoteRoot)` + 一次 `Directory.EnumerateFileSystemEntries(remoteRoot, "*", TopDirectoryOnly).Take(1)` 试探（低成本，验证 SMB 会话仍活着）。
2. 若失败：本轮全部跳过、写 `Error` 日志、进入退避重连（服务用 `WNetAddConnection2` 重新建立凭据连接）。
3. **服务运行形态**（已修订）：USN Journal 需要提权，因此服务必须以 **`LocalSystem`（或管理员账户）** 运行；而 SMB 凭据属于用户会话——两者用“提权 + 显式连接”解决，而不是靠“用哪个用户登录”：
   - 方案 A（**定稿**）：Windows 服务 `obj= LocalSystem`，启动时用 `WNetAddConnection2`（凭据存 DPAPI / 凭据管理器）建立 UNC 会话，配置里一律用 UNC 路径。
   - 方案 B：计划任务 `/ru SYSTEM`（等效，便于手动调试）。
   - 方案 C：交互式前台运行（调试用，同样需提权才能启用 USN）。
   - 三者在 `Program.cs` 中同一套 `IHost` 逻辑，仅安装脚本不同。

### 7.3 编辑中文件的“完成判定”状态机（核心体验点）

```
Changed/Created 事件
      │
      ▼
[Pending] ──(同路径新事件到达则重置计时)──┐
      │  静默 ≥ DebounceQuietMs(默认 3000)  │
      ▼                                     │
[Probe] 尝试 FileStream(path, Open, Read, FileShare.Read)  ← 独占写者存在则抛 IOException
      │  失败 ──(退避 1s/2s/4s…上限 5min，总超时 30min)────┘
      ▼ 成功
[Stable] 记录 size/mtime → 等待 1s → 再读一次，二者一致？（防“打开成功后仍在追加”）
      │  不一致 → 回到 [Pending]
      ▼
[Enqueue] → DiffEngine → 执行同步
```

补充规则（针对 Office/WPS/Adobe）：

- **忽略/挂起 `~$xxx.docx`、`~$xxx.xlsx`、`.~lock.*`、`*.tmp`、`*.crdownload`、`*.part` 等临时文件**；但把 `~$` 文件当作“该文档正被编辑”的信号：检测到 `~$name.ext` 存在时，即使 `name.ext` 能被共享读打开，也**等待锁文件消失**再同步（避免同步到“半保存”的中间态）。
- 识别 `Saved` 特征：Office 保存是 “写临时文件 → rename 覆盖”。因此最终事件通常是 `Renamed`/`Created`+`Deleted(tmp)`，状态机天然收敛。
- 提交前对源文件做**内容哈希**并写入 `sync_log`，用户可在日志里核对“同步的是哪个版本”。
- 静默窗口、探测超时、总超时可配（`debounceQuietMs` / `probeTimeoutMs` / `maxWaitMinutes`）。

### 7.4 防回环（自己写的文件不能再触发同步）

1. 执行器在写文件前对目标路径登记 `self-write` 标记（`path → ts, hash`），Watcher 收到事件时若命中且未过期（默认 15s）→ 丢弃。
2. 即使漏判，DiffEngine 也会因 `L==B` 或 `L==R` 判为 `None`，**不会产生传输**（这是状态化的额外好处）。
3. 兜底扫描间隔：默认 5 分钟（增量、只读元数据），10 分钟一次全量 `Level 2` 快指纹校验（可配 `fullRescanMinutes=0` 关闭）。

## 8. 日志与可观测性

三路输出，全部带上 `run_id` 便于串起一次同步：

| 目标 | 内容 | 保留策略 |
|---|---|---|
| `sync_log`（SQLite） | 结构化事件：每个文件的 op/direction/bytes/duration/hash/错误 | 默认 90 天、上限 200 MB，按天清理（`DELETE ... WHERE ts < ?`） |
| `logs/filesync-YYYYMMDD.log`（Serilog 滚动） | 人读明细 + 异常堆栈 | 单文件 20 MB，保留 14 个 |
| Console（`--once`/`--foreground`） | 实时进度 | — |

CLI 查询能力（不做 GUI 也能审计）：

```bash
filesync logs --since 2024-01-01 --path "docs/*" --op Push --limit 200
filesync status                 # 待同步数、最近一次 run 统计、失败项、远端连通性
filesync conflicts              # 冲突副本清单
filesync sync --once --dry-run  # 只出计划不执行（行首标 Push/Pull/Conflict/Delete）
filesync sync --once --force-deletes
```

日志脱敏：路径按配置可只记录相对路径，不记录完整 UNC（避免泄露 NAS 地址/凭据）。
凭据只通过 DPAPI 加密（`ProtectedData`）或 Windows 凭据管理器存储，**任何日志不得出现密码**。

## 9. 内存控制设计

> ⚠️ **本节数值已过时**：现行目标是引擎稳态 <40MB / 峰值 <50MB，且内存与文件数无关。
> 以 `docs/优化方案-USN与内存.md` §11（实测表）与 §12（merge-walk 预算）为准；下表的“不得整文件读入内存 / ArrayPool / 有界队列”等原则仍然有效。

| 风险点 | 具体做法 |
|---|---|
| 复制大文件 | **绝不 `File.ReadAllBytes`**。`FileStream`(源, 128KB buffer, SequentialScan) → 目标 `.filesync-tmp` `FileStream` → `CopyToAsync` + `IncrementalHash` 同步计算；内存占用 = 缓冲区数量 × 128KB |
| 缓冲区分配 | `ArrayPool<byte>.Shared.Rent(128*1024)`，用完 `Return`；池化上限默认 8 个缓冲（1MB 噪声级） |
| 并发 | 传输并发默认 2（可配 1–4）；每个并发只占 1 个缓冲 + 1 个哈希上下文（≈256KB） |
| 目录枚举 | `EnumerateFileSystemEntries` **流式**枚举，边枚举边判重、边写库（批量 500 条/事务），不构造全量 `List` |
| 事件洪泛 | `ConcurrentDictionary<string, PendingChange>` 按路径合并（同一路径只留 1 条），容量上限 50,000，超出则丢弃明细并置位 `NeedFullRescan` |
| 队列背压 | `Channel.CreateBounded<Job>(capacity: 10_000)` + `BoundedChannelFullMode.Wait` 或 `DropOldest`+全量扫描标志；生产者（Watcher）永远不被消费者阻塞太久 |
| 差量集合 | `SyncPlan` 用 `IReadOnlyList` + 直接流式消费（`IAsyncEnumerable<SyncAction>`），海量变更时不一次性驻留计划 |
| SQLite | 单连接串行写、`PRAGMA cache_size=-8000`（8MB）、批量事务、`Prepare` 复用命令；**不用** EF/DataTable |
| 字符串/路径 | 统一 `ReadOnlySpan<char>` 处理相对路径；不做 `Path.GetFullPath` 循环拼接；大小写不敏感比较用 `StringComparer.OrdinalIgnoreCase` 预建字典 |
| GC/宿主配置 | `ServerGC=false`、`Concurrent=true`、`TieredPGO`；`<InvariantGlobalization>true</InvariantGlobalization>`；R2R 发布；`DOTNET_GCConserveMemory=5`（保守回收，进一步压工作集） |
| 可观测 | `--stats` 输出 `GC.GetTotalMemory`、活跃缓冲数、队列长度、待同步项，便于压测 |

**压测验收线**：10 万个小文件（1KB）首轮全量索引 + 200 个 100MB 大文件复制，峰值工作集 ≤ 200 MB、稳态 ≤ 80 MB；复制 100MB 文件期间 GC Gen2 次数 = 0。

## 13. 风险清单与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| SMB 事件丢失 | 部分改动不实时 | 5/10 分钟兜底扫描 + `Error` 事件立即扫描（§7.1） |
| 映射盘在服务会话不可见 | 完全不同步 | UNC 一等公民 + `LogOnAs` 指定用户账户 / 计划任务（§7.2） |
| 扫描时 NAS 离线被当成“全删” | **数据丢失** | 探针 + 删除比例阈值 + 默认回收区而非真删（§7.2/§6.2） |
| 编辑中文件读到半成品 | 远端文件损坏 | 独占探测 + 稳定窗口 + `~$` 感知 + 原子 rename（§7.3） |
| 两端同时改 | 覆盖丢数据 | 冲突副本（默认 KeepBoth）+ 日志可追溯 |
| 海量小文件扫描慢 | 首轮耗时长 | 流式枚举 + 批量事务 + `Level 1` 快速比较；首轮可 `--hash-mode metadata` |
| 大小写/非法字符差异（NAS 为 Linux） | 同步失败 | 路径规范化：大小写不敏感键 + 非法字符（`:` `*` `?` 等）预检并记 `Skip` 告警 |
| 磁盘满是符号链接/长路径 | 异常 | `\\?\` 长路径、跳过 reparse point（默认不跟随 junction/symlink） |
| 内存膨胀 | OOM | §9 全部措施 + 压测门槛 |

## 14. 测试清单（先行于实现）

1. `DiffEngine` 表驱动：12 行动作矩阵 ×（B 存在/不存在）×（类型 File/Dir）×（Delete 策略）。
2. 大小文件混合：1KB / 10MB / 2GB（稀疏）复制，验证内存平稳与哈希一致。
3. 冲突：两端同时改 → KeepBoth/PreferNewer 各一次。
4. 改名：本地 rename 10 个文件 → 远端只做 rename（用日志 `op=MoveRemote` 断言无 `bytes>0`）。
5. 编辑语义：模拟“写一半 → 停 5s → 继续写 → 关闭” → 只同步一次且内容为最终版。
6. 中断：复制 1GB 中途 kill → 重启后清理临时文件并重传。
7. 断网：断开 Z: → 不删任何文件、日志 Error、恢复后自愈。
8. 回环：同步完成后 60s 内无新增传输（`sync_log` 计数不变）。
9. 安全：删除 30% 文件 → 触发阈值保护退出码 3 且不做删除。

## 15. 备选/逃生路线

- 只想“够用、不写代码”：FreeFileSync（双向 + 数据库 + 实时监控 RealTimeSync）或 Syncthing（需 NAS 端 agent）。**若你后续改主意，本方案的 SQLite 状态模型与它们同构，迁移成本低。**
- 只需单向备份：`robocopy /MIR /Z /R:3 /W:5 /LOG+` 即可，不需要本工具。
- 后续可加（不在本期）：块级增量（rsync 算法，参照 `deajan/osync` + `librsync`）、文件系统 USN 日志加速本地扫描、托盘 GUI（Avalonia/WinForms）。
