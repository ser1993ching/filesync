# 监控设计（定稿）｜文件变化是怎么被发现的

> 已定决策：**① 允许以管理员/LocalSystem 运行 → 本地 NTFS 侧启用 USN Journal；② 状态后端默认 `journal`（纯托管，无 SQLite）。**
> 配套：`docs/PRD.md`、`docs/骨架图.md`、`docs/优化方案-USN与内存.md`、`docs/变体方案-无SQLite与本地双盘.md`。

---

## 0. 一句话概括

> **双通道 + 一次合并 + 一次稳定化 + 一条对账 + 一个自检**：
> FileSystemWatcher 抢低延迟、USN Journal 保不丢（本地 NTFS）、周期对账兜底（SMB 侧唯一保证）、
> 事件先按"目录"合并成脏目录集合，再由 merge-walk 逐目录核对（事件只是提示，**文件系统状态才是真相**）。

关键原则（决定了后面所有设计）：

| 原则 | 含义 |
|---|---|
| **事件是提示，不是事实** | 任何事件都只用来"标记脏目录"，真正要同步什么，由 merge-walk 重新 stat + 比对基线决定。这样事件重复/乱序/丢失都不会造成错误，最差只是不同步。 |
| **不靠事件判删除** | 删除必须由扫描确认"这一侧确实不存在"，且过阈值保护，才执行。 |
| **双通道互补** | FSW = 低延迟（毫秒级），USN = 完整性（可补读）。两者对同一路径的重复提示被合并。 |
| **SMB 只能"通知 + 对账"** | NAS 侧没有 USN，事件必丢，所以周期对账就是正确性保证，实时性只是体验优化。 |

## 1. 分层结构

```
┌ Layer 1 事件源（每侧一个或多个）────────────────────────────────────┐
│  A. FileSystemWatcher (ReadDirectoryChangesW)   本地 + SMB 都能用     │
│  B. USN Journal 轮询 (FSCTL_READ_USN_JOURNAL)   仅本地 NTFS + 提权    │
│  C. Scheduler 对账：本地 30–60min / SMB 5min 增量 / 10–60min 全量校验 │
└──────────────────────────────┬───────────────────────────────────────┘
                               │  只产出「脏目录」「脏路径」提示
┌ Layer 2 合并与去重 ───────────▼───────────────────────────────────────┐
│  dirtyDirs: 有界集合(4096)  +  dirtyPaths: 环形缓冲(8k)               │
│  同路径同目录多次提示 → 一次；溢出 → 置 NeedFullRescan（宁多扫不漏）   │
└──────────────────────────────┬───────────────────────────────────────┘
┌ Layer 3 稳定化（"改完了吗"）───▼───────────────────────────────────────┐
│  静默窗口 debounce(本地2s / SMB3s) → 锁文件(~$) → 独占探测 → 二次复核  │
└──────────────────────────────┬───────────────────────────────────────┘
┌ Layer 4 核对与执行 ───────────▼───────────────────────────────────────┐
│  merge-walk(脏目录) → Decide() → 动作 → 执行 → journal + 基线        │
└──────────────────────────────┬───────────────────────────────────────┘
┌ Layer 5 自检与上报 ───────────▼───────────────────────────────────────┐
│  monitor-mode / 落后 usn / 丢弃事件数 / 脏目录数 → status 与日志       │
└──────────────────────────────────────────────────────────────────────┘
```

## 2. Layer 1：三路事件源怎么配

### 2.1 能力探测决定通道（启动一次）

| 侧的特征 | FSW | USN 轮询 | 对账频率 |
|---|---|---|---|
| 本地 NTFS + 已提权 | ✅ 低延迟 | ✅ **正确性保证** | 增量 60min / 全量 6h（USN 已兜底） |
| 本地 NTFS + 未提权 | ✅ | ❌ | 增量 10min / 全量 1h |
| 可移动卷 exFAT/FAT32 | ✅ | ❌（非 NTFS） | 增量 10min / 全量 1h，mtime 容差 2s |
| SMB / 映射盘（UNC） | ✅（会丢） | ❌（无法远程读日志） | **增量 5min / 全量 10–60min** |

写入 `status`：`monitor[a]=fsw+usn mode=usn polled=0x0000000d5d9df868 behind=0`、`monitor[b]=fsw mode=fsw rescan=5min`。

### 2.2 A. FileSystemWatcher（每侧一个，本地与 SMB 通用）

```csharp
var fsw = new FileSystemWatcher(root) {
    IncludeSubdirectories = true,
    NotifyFilter = NotifyFilters.FileName | NotifyFilters.DirectoryName
                 | NotifyFilters.LastWrite | NotifyFilters.Size,
    InternalBufferSize = 64 * 1024,      // 上限，降低溢出概率
    EnableRaisingEvents = true,
};
fsw.Created += (_, e) => Mark(a, e.FullPath);
fsw.Changed += (_, e) => Mark(a, e.FullPath);
fsw.Deleted += (_, e) => Mark(a, e.FullPath);
fsw.Renamed += (_, e) => { Mark(a, e.OldFullPath); Mark(a, e.FullPath); };
fsw.Error   += (_, e) => {                      // InternalBufferOverflow 等
    Log.Warn("watcher-overflow side={0}", a);
    MarkSideDirty(a);                           // 立刻对该侧做一次增量对账
};
```

- **SMB 上的 FSW 一定报 `Error`**：只要 NAS 侧一次变动 > 64KB 通知量（例如解压、批量删除），就必须靠 §2.4 对账补回。
- FSW 只负责 `Mark()`（把路径归一到所在目录），不做任何 IO。

### 2.3 B. USN Journal 轮询（本地 NTFS，1s 一次）

```csharp
// 启动：读检查点 → 校验有效性 → 从 nextUsn 开始读
var j = QueryJournal(volHandle);                       // FSCTL_QUERY_USN_JOURNAL
if (cp is null || cp.JournalId != j.UsnJournalID || j.FirstUsn > cp.NextUsn) {
    Log.Warn("usn-invalidated");  FullBaselineRebuild(); // 全量重建（见 §2.5）
    cp = new(j.UsnJournalID, j.NextUsn);
}

// 每 1s：读增量（通常 0 条）
var input = new READ_USN_JOURNAL_DATA_V0 {
    StartUsn = cp.NextUsn,
    ReasonMask = USN_REASON_FILE_CREATE | USN_REASON_FILE_DELETE
               | USN_REASON_RENAME_OLD_NAME | USN_REASON_RENAME_NEW_NAME
               | USN_REASON_DATA_OVERWRITE | USN_REASON_DATA_EXTEND
               | USN_REASON_DATA_TRUNCATION | USN_REASON_BASIC_INFO_CHANGE
               | USN_REASON_CLOSE,
    ReturnOnlyOnClose = 1,        // ★ 句柄关闭才上报：写入噪声被内核合并（编辑完成后恰好一次）
    Timeout = 0, BytesToWaitFor = 0,
};
```

| Reason 位 | 值 | 我们的处理 |
|---|---|---|
| `DATA_OVERWRITE / EXTEND / TRUNCATION` | 0x1 / 0x2 / 0x4 | 标脏该文件所在目录 |
| `FILE_CREATE` | 0x100 | 标脏 |
| `FILE_DELETE` | 0x200 | 标脏（删除仍由扫描确认，不凭此删） |
| `RENAME_OLD_NAME` / `RENAME_NEW_NAME` | 0x1000 / 0x2000 | 成对配对 → 得到 `Move(FRN)`，标脏两侧目录 |
| `BASIC_INFO_CHANGE` | 0x8000 | 标脏（属性/时间戳变化） |
| `CLOSE` | 0x80000000 | 配合 `ReturnOnlyOnClose=1`，等价"这个文件写完了" |

要点：

1. **`ReturnOnlyOnClose = 1`** 让内核把"打开→写 N 次→关闭"合并成一条记录，天然实现"编辑完成后上报一次"。副作用是**长期保持打开的文件不报**（例如某程序一直握着句柄），所以仍需 FSW + 对账兜底。
2. **顺序铁律**：读到本批次记录后，先把它展开成“脏目录待办”并 **fsync**（`DirtyTodo` 记录），**然后才**把 `nextUsn` 写进 journal。
   反过来（先推进 USN 后处理）在崩溃时会**永久丢事件**；按此顺序崩溃最多重复处理一批，而 merge-walk 幂等，重复无害。
3. **FRN 让改名 O(1)**：`RENAME_OLD_NAME`/`RENAME_NEW_NAME` 同 `FileReferenceNumber`，配对得到 (旧路径, 新路径)，不需要哈希搜索；路径解析用 `OpenFileById` + `GetFinalPathNameByHandle`，仅对改名对做（量极小）。
4. 若一轮读到 `ret <= 8`（无记录）直接跳过，**CPU 占用接近 0**。
5. 轮询间隔 1s vs 期刊 32MB：一次爆发要产生 >32MB USN（约 10 万次变更）才会越界，届时按 §2.5 降级。

### 2.4 C. 调度对账（唯一能覆盖 SMB 正确性的手段）

| 侧 | 增量对账 | 全量校验（含快哈希） | 说明 |
|---|---|---|---|
| 本地 + USN | 60min | 6h | USN 已保证不丢，对账只是"防 FRN 复用/软件 bug" |
| 本地 + FSW | 10min | 1h | FSW 溢出靠它补 |
| SMB | **5min** | 10–60min（可配） | 唯一保证；5min 的代价是走一次目录树（用 `FindExInfoBasic`，只读元数据） |

对账不是"全量 diff"，而是：**遍历 → 生成脏目录集合 → 只把与基线不一致的目录交给 merge-walk**。目录级快速跳过：两侧目录 mtime + 条目数与基线一致 → 不下钻（只省 IO，内容修改仍由事件/全量校验兜底）。

### 2.5 失效与降级路径（必须实现，否则会静默漏同步）

| 触发 | 处理 |
|---|---|
| USN 句柄打不开（提权丢失/非 NTFS） | 该侧降为 FSW 模式，`status` 与日志标注原因，对账频率自动提高 |
| `JournalId` 变化 / `FirstUsn > checkpoint` | 作废检查点 → 该侧全量重建基线 → 恢复 USN |
| FSW `Error`（溢出） | 立刻一次增量对账；连续 3 次溢出 → 缩短对账间隔并告警 |
| 脏目录集合溢出（>4096） | 丢弃明细 + `NeedFullRescan=true` → 全量对账一次 |
| 对账发现"远端不可枚举" | 本轮跳过（退出码 4 语义），**绝不把离线当全删** |

## 3. Layer 2：合并（事件 → 脏目录）

```csharp
// 事件只做两件事：归一化、去重。内存有界，永不 OOM。
void Mark(Side side, string fullPath)
{
    var dir = Path.GetDirectoryName(fullPath)!;        // 事件粒度收敛到"目录"
    if (IsIgnored(dir, fullPath)) return;
    if (_selfWrites.TryConsume(side, dir)) return;     // 自己写的，丢掉
    if (!_dirty[side].TryAdd(dir)) _overflow[side] = true;   // 上限 4096
}
```

- 一个目录内改 1000 个文件 → **只产生 1 个脏目录**，后续 merge-walk 一次遍历解决。
- 上限溢出只是"多扫一次全量"，不会丢正确性。
- 同一目录并发处理用**每目录信号量**串行化，避免两轮同时写同一目标文件。

## 4. Layer 3：稳定化（这才是"编辑完成后同步"的关键）

```
脏目录 → 取出候选文件 → 逐个走稳定化闸门
  ① 忽略名单：~$*, *.tmp, *.crdownload, .filesync-*, Thumbs.db …
  ② 锁文件：同目录存在 ~$<name> 或 .~lock.<name># → 明确正在编辑 → 挂起（不占线程，进等待表）
  ③ 独占探测：FileStream(FileShare.None) 打开成功？失败 → 退避 1s/2s/4s…30s
  ④ 二次复核：1s 后再读 size + mtimeWrite，与 ③ 一致？不一致 → 回 ①
  ⑤ 通过 → 进入 Decide()
超过 maxWaitMinutes(30) 仍被占用 → Warn + 本轮跳过（事件/对账会再次触发）
```

> 注意：`ReturnOnlyOnClose=1` 会让“长时间保持句柄打开”的文件迟迟不上报，且个别 NAS/过滤驱动对结构变更（删除/改名）的上报语义存在差异。
> **落地要求**：首版先以 `ReturnOnlyOnClose=0` + 自身按路径合并运行（正确性优先），同时在测试环境验证 `=1` 的收益与回归（M2/M6 用例），通过开关 `monitoring.returnOnlyOnClose` 切换。

## 5. Layer 4：核对与执行（事件只是线索）

```
merge-walk(脏目录, 两侧):
    列举 A 目录条目（流式） / 列举 B 目录条目（流式）
    对每个条目：查 journal 基线 → Decide(l, r, base)
        动作 = Push / Pull / Move / Conflict / Delete / None
    执行（顺序：建目录 → 改名 → 传输 → 删除）
    写 journal：基线 + 日志（同一条追加记录）
    递归子目录
```

三个"凭事件不做判断"的反例，说明为什么必须回到文件系统状态：

| 场景 | 若相信事件 | 实际处理 |
|---|---|---|
| Office 保存 | 事件顺序 `Deleted(原件) → Created(临时) → Renamed(临时→原件)`，中间态会被误删 | 合并到同一脏目录，扫描时看到的只有"存在"的文件，事件顺序无关 |
| 远端短暂不可达导致 `Deleted` 风暴 | 会清空本地 | 删除必须扫描确认 + 阈值保护 + 回收区 |
| 自己写入触发事件 | 会无限回环 | `self-write` 抑制 + 基线判等 |

### 删除与目录规则（防丢数据）

| 情形 | 规则 |
|---|---|
| 文件删除 | 扫描确认该侧不存在 + 阈值保护 → 目标端进 `data\trash\`（不直删） |
| **目录删除** | **展开为逐条决策**：目标端子树内若有“相对基线变过”的文件 → 不整树删，逐个 Conflict/保留 |
| **目录改名** | 一等动作 `MoveDir`（USN 的 RENAME 成对记录 + FRN）；目标端同卷 `Directory.Move`，**不整树重传** |

### 与首轮/UI 的接口（速查）

- `init` 阶段不调用本文件任何写路径：只读清点 + 写 `reports/firstrun.*` + 指纹。
- UI 只读 `stats/page`；所有决策回引擎校验指纹后再落 `InitDecision`。

## 6. 延迟预算(本地双盘 C⇄D,USN 生效)

| 阶段 | 耗时 |
|---|---|
| 编辑保存 → FSW 立刻命中 / USN 1s 内 | 0–1s |
| 静默窗口（本地 2s） | 2s |
| 独占探测 + 二次复核 | ~1s |
| merge-walk 该目录（≤2000 条） | 10–50ms |
| 小文件复制 | ms 级 |
| **合计** | **约 3–4s**（SMB 侧 4–6s） |

## 8. 测试（监控专项）

| # | 用例 | 判据 |
|---|---|---|
| M1 | 同一文件连续保存 20 次（Word） | 只同步 1 次，内容为最终版；日志有 `locked-by-office` 记录 |
| M2 | 解压 5 万文件到被监听目录 | 不丢文件（对账补齐）；脏目录数受控；内存不涨 |
| M3 | 手工 `fsutil usn deletejournal /d C:` 后恢复 | 自动全量重建，不漏同步 |
| M4 | 以非管理员启动 | 降级 fsw，`status` 显示原因，功能完整 |
| M5 | 拔网线 30 分钟后恢复 | SMB 侧 5min 内补齐；无删除 |
| M6 | 1 万次快速改名 | Move 判定 O(1)，无内容传输 |
| M7 | 同步器自己写入 1000 个文件 | 无回环（`eventsCoalesced` 增长但 `Push/Pull` 计数不变） |
| M8 | kill -9 后重启 | USN 检查点续读，无重复传输、无漏同步 |
