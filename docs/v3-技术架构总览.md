# FileSync Technical Architecture v3.0

> 状态：架构基线（Architecture Baseline）
> 日期：2026-11-23
> 适用范围：技术验证、模块设计、实现、测试与发布评审。
> 产品硬约束：Windows x64、.NET 8、无 SQLite、低内存、本地目录与 NAS/SMB 双向同步。

## 1. v3.0 的目标

v2.0 已明确产品范围，但专题文档仍存在旧实现假设，例如“文件落盘与 Base 天然原子”“目录 mtime/条目数可跳过子树”“quick hash 可证明文件未变化”“服务 LocalSystem 与映射盘可直接组合”等。v3.0 将这些概念改成可编码、可测试、可恢复的工程规则。

本版本不推翻用户已经确认的产品决策；它收紧实现语义，避免把优化假设误当正确性保证。

## 2. 决策登记

| 决策 | 当前结论 | 备注 |
|---|---|---|
| 目标框架 | .NET 8 | 保留用户决定；记录生命周期风险 |
| 状态存储 | 纯托管 Journal + Snapshot | 不引入 SQLite；必须承担数据库级恢复责任 |
| 同步方向 | A/B 对等，默认 TwoWay | NAS → 本地与本地 → NAS 同等重要 |
| NAS 接入 | SMB/UNC，无 NAS Agent | NAS 事件不作为唯一变化事实 |
| 内存 | 核心产品约束 | 有界缓存、队列、Worker、磁盘索引 |
| 冲突 | 默认 KeepBoth | 不确定时保留双方版本 |
| 删除 | 默认回收区 + 熔断 | 不可访问/扫描不完整绝不传播删除 |
| UI | 独立 Win32 + GDI 轻量进程 | 不允许 UI 绕过 Engine 直接写文件 |
| 监控 | FSW + 可选 USN + 周期对账 | 监控提示不等于完整变化日志 |

### 2.1 .NET 8 生命周期风险

截至 2026-11-23，Microsoft 已于 2026-11-10 结束 .NET 8 支持；该版本继续运行不代表仍有安全维护。此处记录事实与风险，不擅自更改用户指定的目标框架。发布前应由产品负责人确认风险接受，并把运行时升级作为独立决策评审。

## 3. 逻辑架构

~~~text
                 FileSync.Ui (Win32 + GDI)
                           |
                     IPC / Commands
                           |
                    FileSync.Host
             lifecycle / task / CLI / IPC
                           |
                    FileSync.Engine
       Scanner -> Reconciler -> Planner -> Executor
             |           |          |        |
             +-----------+----------+--------+
                           |
                    FileSync.Core
      ThreeWayMerge / SyncDecision / ConflictResolver
                           |
                FileSync.Abstractions
       IFileSystemEndpoint / IStateStore / IChangeSource
                           |
       +-------------------+--------------------+
       |                   |                    |
 FileSync.Storage   Platform.Windows       Test Fakes
 Journal/Snapshot   NTFS/SMB/USN/FSW       FakeEndpoint
~~~

依赖方向只能向下。Core 不引用 Windows API、SMB、UI、日志实现或具体状态存储。Storage 不负责同步决策。UI 通过 Host/IPC 发命令和读取分页结果，不能直接修改基线或文件。

## 5. 核心数据流

1. Host 验证配置、端点、权限和任务租约。
2. Scanner 创建带完整性标记的 ScanEpoch，流式枚举 A/B。
3. Reconciler 将扫描观察与 Base 合并；Unknown/Incomplete 不产生删除结论。
4. Planner 生成持久化、可复核的 SyncPlan。
5. Executor 对每项操作重新验证前置条件，按 Operation 状态机执行。
6. Storage 持久化 Operation 结果与 Base 更新。
7. ChangeSource 将变化作为 Dirty 提示；溢出/失效触发对账。
8. UI 展示任务状态、扫描完整性、冲突、恢复项和最近完整对账时间。

## 6. 并发模型

第一版不引入复杂 Actor 框架。采用：
- 每个 Task 一个逻辑调度器；
- 每个 Task 一个串行状态提交者；
- 每路径互斥，防止本进程同一路径并发；
- 有界 Worker Pool；
- 默认传输并发 1，实测后最多可配置到 2；
- 有界事件队列和磁盘化重试队列；
- 跨客户端通过 NAS 租约协调；不支持可靠租约的 NAS 禁止同一任务多客户端同时运行。

任何队列满、租约失效、状态库写入失败，都必须显式停止或转入补偿流程，不能静默丢状态。

## 7. 监控与一致性承诺

产品对外承诺“实时监控 + 最终一致性保障”，不承诺所有 NAS 固定秒级完成。FSW、USN、SMB Change Notification 都可能失效或丢事件。端点变化最终通过周期对账和必要的内容审计发现。

NAS 对账需考虑网络 IO：采用分级扫描、限速、空闲时段审计和可配置周期；但任何“跳过子树”优化都必须有可信变化序列支撑，不能仅凭目录时间或条目数。

## 8. 开发路线

### 阶段 0：技术验证（先做）

- 真实 Windows NTFS 与至少两种 SMB 服务端的能力探测；
- SMB 断线/重连、权限变化、文件锁、重命名、Flush/替换语义；
- Journal 半写、崩溃恢复、文件提交与 Base 不一致恢复；
- 三方状态机与随机模型测试；
- 10 万/100 万文件流式扫描和内存曲线；
- NAS 任务租约与双客户端竞争。

退出条件：关键语义有可复现实验结论；不可靠能力有安全降级方案。不得跳过阶段 0 直接大规模编码。

### 阶段 1：可靠同步核心
端点抽象、扫描、三方判定、计划、Journal、事务执行、回收区、恢复。

### 阶段 2：NAS 双向
UNC/SMB、NAS 拉取与推送、断线保护、租约、真实 NAS 验收。

### 阶段 3：持续监控
FSW、USN 增量、队列溢出、周期对账、稳定性闸门。

### 阶段 4：轻量 UI
任务列表、首次同步预览、进度、冲突中心、恢复中心、日志与设置。

### 阶段 5：性能与发布
低内存优化、长稳、压力测试、兼容性、发布包和升级风险评审。

## 9. 禁止实现的错误假设

- 不得认为文件系统操作与 Journal 可以天然原子提交。
- 不得认为 size + mtime + 头尾 quick hash 可证明内容未变。
- 不得仅凭目录 mtime/条目数跳过 NAS 子树。
- 不得把 NAS 不可达、权限错误、枚举失败解释成删除。
- 不得认为本机 Mutex 能阻止其他电脑同时运行任务。
- 不得无条件清理所有临时文件。
- 不得用 GC HeapHardLimit 代替进程总内存预算。
- 不得把 SMB 服务端的成功响应解释为绝对持久化保证。

## 10. 变更控制

任何架构决策变更必须：
1. 在决策记录中说明原因、替代方案与数据安全影响；
2. 更新对应 v3 专题规范；
3. 更新 PRD/验收用例（若用户行为改变）；
4. 增加自动化测试或故障注入证据；
5. 通过独立 PR 审阅。

不得在代码中静默改变 .NET 目标框架、SQLite 决策、同步方向、删除默认策略或内存目标。
