# FileSync v3.0：文件操作事务与崩溃恢复

> 状态：实现规范（Normative）
> 本文与《同步引擎与三方状态机》共同定义数据安全边界。文件系统操作与本地状态库不具备跨资源原子事务，必须使用可恢复操作协议。

## 1. 设计目标与边界

FileSync 无法把 SMB/NTFS 文件替换和本地 journal 写入包装成一个真正的 ACID 事务。因此不得宣称“文件落盘与基线更新天然原子”。正确目标是：
- 操作意图先持久化；
- 文件写入采用目标目录内临时文件；
- 校验后以端点能力支持的安全提交方式替换；
- 每个阶段有持久状态和 OperationId；
- 崩溃后通过检查真实文件状态幂等恢复；
- 无法证明安全时暂停，不盲目覆盖、删除或清理现场。

第一版不承诺跨两个文件系统的原子事务，也不承诺 NAS 端支持 NTFS 同等级的原子替换语义。

## 2. Operation 状态机

建议状态如下：

~~~text
Planned
  -> Prepared
  -> TempCreated
  -> Copying
  -> TempFlushed
  -> Verified
  -> CommitIntent
  -> TargetCommitted
  -> OperationCommitted
  -> BaselineUpdated
  -> Completed
~~~

异常状态：
- Retryable：网络暂断、共享忙、短暂锁定；保留操作上下文。
- StaleSource：源端在读取期间变化；丢弃临时文件或隔离后重试。
- TargetChanged：目标端被外部修改；重新判定，不得直接覆盖。
- RecoveryRequired：崩溃后无法从日志和文件状态唯一确定结果。
- Aborted：明确安全取消，完成必要清理并记录原因。

状态转换规则：
1. 每次状态转换先追加 journal 记录并按持久化策略 Flush；只有持久化成功才向下执行。
2. OperationId 全程不变；重试创建新的 AttemptId，不创建语义重复的 Operation。
3. 状态只能向前或进入显式异常态，不允许将旧状态覆盖成看似完成。
4. 同一 Operation 的状态更新由单一状态提交者串行完成。

## 3. 文件复制提交协议

### 3.1 准备阶段

- 校验任务租约、端点可用性、目标父目录权限和剩余空间（空间检查只是提示，写入仍需处理磁盘满）。
- 重新校验源端身份、大小、时间与计划指纹；目标端必须符合计划中的预期状态。
- 生成唯一 OperationId 和目标临时路径；临时文件必须位于目标文件同一目录或同一卷，以提高原子重命名成功概率。
- 将 Prepared 记录写入 journal，包含源/目标相对路径、临时路径、预期旧目标指纹、源摘要、目标端能力、创建时间。

### 3.2 写入阶段

- 创建临时文件时使用不覆盖既有文件的唯一名称。
- 流式复制，固定大小缓冲区；禁止整文件进入内存。
- 复制期间统计字节数，处理短读、短写、取消、超时和 SMB 断线。
- 完成后 Flush 文件数据；平台允许时请求持久化刷新。SMB/NAS 对 Flush 的真实持久化保证取决于服务器实现，不能夸大。
- 复核源端仍与开始时一致；不一致则标记 StaleSource。
- 对临时文件重新计算完整 SHA-256，并与源摘要比对。长度和摘要不一致不得提交。

### 3.3 提交阶段

- 持久化 Verified 和 CommitIntent。
- 再次检查目标现状，防止计划生成后被外部程序修改。
- 如果目标原本不存在，使用不覆盖式移动/重命名；如果目标存在，先将旧版本移入回收区或版本区，再提交新文件。
- 目标端不支持可靠的原子替换/重命名时，采用显式降级协议：保留旧版本、写入新文件、验证、切换；如果无法保证不丢数据，则拒绝自动覆盖并要求用户处理。
- 提交后重新读取目标长度和完整指纹，确认目标正式路径确为预期内容。
- 依次写入 TargetCommitted、OperationCommitted、BaselineUpdated、Completed。每一步持久化成功后才更新内存视图。

## 4. 覆盖与删除协议

### 4.1 覆盖

覆盖不是简单的 CopyFile(overwrite=true)。必须：
1. 把旧目标内容移动到任务隔离的版本/回收区；
2. 记录旧目标完整路径、内容指纹、回收位置和 OperationId；
3. 提交新版本；
4. 校验新版本；
5. 更新 Base。

若旧版本无法安全保存，默认停止覆盖。用户显式关闭版本保护时，必须显示风险并记录审计事件。

### 4.2 删除

- 删除操作必须先生成计划，并通过删除数量/比例熔断。
- 默认将目标移入回收区，不立即永久删除。
- 对目录删除先展开为文件级计划，逐项确认是否有基线变化、未知子树或未解决冲突。
- 移入回收区后验证回收对象存在，再记录删除已提交和墓碑。
- NAS 不可用、权限失败、扫描不完整、租约丢失时，禁止执行基于缺失判断的删除。
- 永久清理仅由独立回收区保留策略执行，且必须可暂停、可审计。

## 5. 启动恢复算法

启动时先进入 Recovery 阶段，不立即启动监控或执行新计划。

对每条未完成 Operation：
1. 读取最后一个有效 journal 状态；CRC/长度错误后的尾部按截断规则处理，并记录损坏位置。
2. 检查目标临时文件是否存在、长度是否符合、是否可重新计算摘要。
3. 检查正式目标路径的内容指纹是否等于预期新内容。
4. 检查回收区旧版本是否存在且与记录匹配。
5. 检查源端是否仍可访问、内容是否仍匹配。
6. 根据证据执行以下决策：

| 观察结果 | 恢复动作 |
|---|---|
| 正式目标内容等于预期新内容，journal 尚未记 TargetCommitted | 补写提交记录，再幂等推进 Base |
| 临时文件完整且校验通过，正式目标仍符合预期旧状态 | 重新执行提交阶段 |
| 临时文件不完整，正式目标仍是旧版本 | 安全删除临时文件，标记 Retryable |
| 正式目标与预期新/旧内容都不匹配 | TargetChanged，停止自动恢复并重新扫描 |
| 旧目标已进入回收区，新目标尚未提交 | 验证回收版本后继续提交；若新提交失败，保留旧版本并报告 |
| 源端已变化，临时文件内容与源预期不符 | 丢弃/隔离临时文件，重新扫描 |
| journal 状态损坏且文件证据不足 | RecoveryRequired，禁止猜测 |

恢复操作必须可重复执行；恢复程序在任意步骤再次崩溃，下次启动仍能根据同一 OperationId 收敛。

## 6. 临时文件清理规则

禁止启动时无条件删除所有 .filesync-tmp 文件。

清理前必须确认：
- 临时文件名能解析出 TaskId/OperationId；
- 不存在仍有效的 Operation 引用；
- 没有有效任务租约或文件句柄；
- 文件不是用户手工创建的同名文件；
- 依据状态日志与目标状态可以证明它是孤儿临时文件。

不能确认归属的文件移入隔离区或保留并报告，不得直接删除。

## 7. Journal 与 Snapshot 持久化

- Journal 采用追加式记录：长度、版本、类型、序号、payload、校验和。
- 每条记录带单调递增 Sequence 和 TaskId；重要操作记录带 OperationId。
- 追加必须处理部分写入、磁盘满、Flush 失败、进程终止。
- 重放只接受连续且校验通过的记录；遇到无效尾部，截断到最后一条完整记录并保留诊断信息。
- Snapshot 采用写新文件、Flush、校验、原子替换 manifest 指针的流程；不能先删旧快照。
- 压实过程必须保证旧 Snapshot + Journal 在新 Snapshot 校验完成前仍可恢复。
- SchemaVersion 必须版本化；未知的未来版本应拒绝写入，不得静默降级。
- 状态存储空间不足时停止新的破坏性操作，进入 StateStoreUnavailable。

## 8. 端点能力降级

每个端点声明：
- 原子创建、同目录重命名、覆盖式替换；
- 文件 Flush、目录 Flush（若可用）；
- 文件 ID、大小写比较规则、时间戳精度；
- 文件锁/共享冲突行为；
- 文件名限制、最大路径长度；
- 断线时句柄和重试语义。

操作前按能力选择提交策略。能力未知按“不保证原子”处理。SMB 服务端报告成功不等于硬件已持久化，文档与 UI 应避免“绝对不丢数据”等承诺。

## 9. 故障注入测试

至少在以下位置强制终止进程或模拟 IO 错误：
- Prepared 记录后；
- 临时文件创建后；
- 复制 1%、50%、99%；
- Flush 前后；
- Verified 后；
- CommitIntent 后；
- 旧目标移入回收区后；
- 新目标重命名后；
- TargetCommitted 后；
- OperationCommitted 后；
- BaselineUpdated 前后；
- journal 半条写入、CRC 错误、磁盘满；
- SMB 断线、权限撤销、目标文件被外部程序替换。

每个场景必须证明：不静默丢失源数据、不把不完整文件作为正式文件、不错误推进 Base、不把远端不可达解释为删除。
